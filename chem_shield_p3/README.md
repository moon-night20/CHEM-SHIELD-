# CHEM-SHIELD AI/ML: Physical-Process Anomaly Detection

The earlier `ML_README.md` content has been merged here; the separate file was
removed to keep the maintained documentation in a single place.

## Purpose and scope

This directory contains the AI/ML physical-process anomaly detector for the CHEM-SHIELD academic prototype. It answers one limited question:

> Does the current physical/process telemetry look anomalous compared with learned normal behavior?

The detector is intentionally limited to simulated motor telemetry and an Isolation Forest baseline. It does not implement network monitoring, Modbus inspection, correlation, risk scoring, automated response, PLC control, or any interaction with real industrial, military, or other operational systems. Part 4 separately accepts normalized events and renders risk in the Part 1 HMI.

**The AI/ML component does not determine overall cybersecurity risk. It provides physical-process anomaly evidence to the separate correlation and risk-engine components.**

## Architecture boundary

```text
OT simulator -> physical telemetry -> feature engineering -> Isolation Forest
             -> physical ML event -> P5 monitor -> Part 4 correlation/risk
```

This module stops after emitting the physical ML event. A physical anomaly is not described as an attack detection.

## Data flow

P3 trains and provides the saved physical model; P5 loads that artifact to score
its validated telemetry, combines model evidence with its independent rule
checks, and can publish scored physical events to the loopback P1 HMI. P3's
standalone scenario runner remains an offline evaluation tool.

## Synthetic laboratory data

All included data is **synthetic laboratory data generated for controlled academic experimentation**. It does not represent real Ethiopian defense-industrial telemetry, a real machine, or a real facility. Results from the supplied scenarios demonstrate pipeline behavior only; they are not real-world performance claims.

## Input telemetry and features

The detector consumes a chronological CSV or `pandas.DataFrame` with:

```text
timestamp,rpm,temperature,pressure,power
```

`timestamp` is required at inference so every event can be integrated downstream. RPM values use the P1 simulator's RPM scale (0–1500), not a normalized 0–100 speed scale. The detector also accepts and preserves useful non-model columns such as `asset_id`, `scenario`, `motor_status`, and evaluation-only `actual_label`. The model uses four measured channels, four per-observation rates, and three physical-consistency residuals:

```text
rpm
temperature
pressure
power
rpm_rate
temperature_rate
pressure_rate
power_rate
power_rpm_residual
temperature_power_residual
pressure_rpm_residual
```

Rates are differences between consecutive observations, measured per observation rather than per second. The residuals describe power vs RPM, temperature rise vs power, and pressure vs RPM against approximate simulator relationships. The first observation in a newly loaded independent stream receives zero rate values. For a streaming caller, the detector maintains the previous sensor state between single-observation calls; callers may reset it with `reset_stream()` or provide `previous_state`. Evaluation scenarios use `scenario` as an explicit independent-stream boundary, so their first rows are also initialized to zero rather than receiving artificial boundary spikes.

Process values are converted to numeric. Short missing runs are linearly interpolated; missing values at either edge use the nearest observed value. A required process column containing no numeric values is rejected. Timestamps must be present and non-decreasing for inference.

## Model and anomaly score

Training uses normal-operation readings generated by the P1 `ProcessUnit`, including start/stop transitions and multiple target RPMs from 0 to 1450, with scikit-learn's `IsolationForest` and `random_state=42`. The default `contamination=0.05` configures Isolation Forest's expected outlier proportion; it can be adjusted deliberately at training time. If an input training CSV includes `actual_label` or `is_anomaly`, every value must explicitly indicate normal behavior (`0` or `False`); otherwise training is rejected.

`is_anomaly` uses Isolation Forest's native binary prediction:

```text
1  -> normal -> is_anomaly=False
-1 -> anomaly -> is_anomaly=True
```

`anomaly_score` is separate from that decision. It is a normalized anomaly-indicator score in `[0, 1]`, where higher values mean stronger deviation from learned normal behavior. It is **not a probability** and is not thresholded to make the binary decision. The saved model calibrates this displayed score from the observed minimum and maximum of negated `score_samples` on the normal training data. The binary decision always remains the model's native decision boundary.

## Setup

From the repository root, install the Part 3 dependencies in the environment
used to run the detector:

```bash
python3 -m pip install -r chem_shield_p3/requirements.txt
```

## Training and inference

Training and inference are deliberately separate: normal telemetry is used to train once, and new telemetry uses the persisted model without retraining.

```bash
cd chem_shield_p3
# Optional: regenerate controlled synthetic inputs
python3 scripts/generate_normal_data.py
python3 scripts/generate_test_scenarios.py

# Train only from normal telemetry and save model plus feature configuration
python3 scripts/train_model.py

# Infer using the existing model; this does not retrain
python3 scripts/run_detection.py \
  --input data/test_scenarios.csv \
  --stream-column scenario \
  --output results/physical_ml_output.csv
```

The default saved artifact is `models/isolation_forest.joblib`. It contains the fitted Isolation Forest, feature order, model settings, rate policy, score calibration, and training metadata needed for compatible inference. Training also writes `models/isolation_forest.metadata.json` with the scikit-learn version. Loading warns when that version differs; if the artifact cannot be unpickled, the error directs you to rerun `python3 scripts/train_model.py`.

## Output contract

`results/physical_ml_output.csv` is machine readable. Each observation includes at least:

```text
timestamp
asset_id
rpm
temperature
pressure
power
rpm_rate
temperature_rate
pressure_rate
power_rate
power_rpm_residual
temperature_power_residual
pressure_rpm_residual
source
is_anomaly
anomaly_score
model
```

The default `asset_id` is `MOTOR-01`; a telemetry `asset_id` is preserved, or a caller may supply one. `source` is always `physical_ml`, and `model` is `IsolationForest`. `model_decision_score` is included for transparent diagnostics and plotting. Optional input columns may be passed through, including synthetic evaluation labels, but no risk, correlation, network, criticality, or attack-type fields are created.

A representative event is:

```json
{
  "timestamp": 123,
  "asset_id": "MOTOR-01",
  "source": "physical_ml",
  "is_anomaly": true,
  "anomaly_score": 0.91,
  "model": "IsolationForest"
}
```

The score shown above is illustrative output shape only, not a measured result.

## Held-out evaluation

`python3 -m chem_shield_p3.scripts.evaluate_heldout` trains a fresh model using
only the P1-simulated normal dataset, then evaluates a separate one-hour normal
run plus the complete `stealthy_in_range` and `slow_gradual_drift` scenarios.
It reports detection rate, first-detection latency in seconds, and false alarms
per hour for each scenario in `results/heldout_scenario_evaluation.csv`. The
current synthetic run detected 87.5% of stealthy-in-range observations and
7.5% of slow gradual drift observations, with 339 false alarms per hour on the
one-hour normal run. These results expose the model's limitations and are not
real-world performance estimates. The summary and exact protocol are recorded
in `results/heldout_evaluation_summary.json`.

## Python API

```python
import pandas as pd
from src.detector import PhysicalAnomalyDetector

normal_data = pd.read_csv("data/normal_data_large.csv")
detector = PhysicalAnomalyDetector().fit(normal_data)
detector.save("models/isolation_forest.joblib")

# A single mapping returns one event dictionary and keeps stream state.
event = detector.predict({
    "timestamp": 1001,
    "rpm": 950,
    "temperature": 50.1,
    "pressure": 2.8,
    "power": 7.5,
    "asset_id": "MOTOR-01",
})

# A DataFrame returns one event row per telemetry observation.
events = detector.predict(pd.read_csv("data/test_scenarios.csv"), stream_column="scenario")
```

For a newly independent single-observation stream, call `detector.reset_stream()` first. Alternatively, provide `previous_state` containing `rpm`, `temperature`, `pressure`, and `power` when the preceding state is managed by another component.

## Part 4 handoff

P3's standalone runner does not publish directly. P5 is the physical-event
producer: it loads this model and, when run with `--publish`, adapts scored
physical events for Part 1's `POST /api/risk/events` endpoint. Preserve the
detector's actual `[0,1]` `anomaly_score`; it is not a probability. The P5
configuration maps its local asset identity to the shared `PLC-01` correlation
asset. An illustrative Part 4 event shape is:

```json
{
  "timestamp": "2026-10-14T09:30:04Z",
  "source": "physical_ml",
  "asset_id": "PLC-01",
  "event_type": "physical",
  "anomaly_score": 0.91,
  "evidence": {
    "adapter_event_type": "physical_ml_anomaly",
    "model": "IsolationForest",
    "is_anomaly": true
  }
}
```

Use `event_type: "physical"` in the normalized Part 4 event; a detailed
detector-specific type such as `physical_ml_anomaly` belongs in evidence. Part
4 retains that evidence and correlates events for the same asset in its
configured time window. The example score illustrates output shape only; it
is not a measured result. See
[Part 4's integration and risk semantics](../chem_shield_p4/correlation/README.md).

## Controlled evaluation

> **Current held-out synthetic results:** a P1-simulated normal-only training
> set was evaluated against complete, unseen attack scenarios. Detection was
> 87.5% for `stealthy_in_range` (first detection at 0 s) and 7.5% for
> `slow_gradual_drift` (0.5 s); the one-hour normal stream produced 339 false
> alarms/hour (4.71% FPR). The prior 97% / 4% headline used only 200
> same-generator samples and is historical, not a current performance claim.
> These metrics are simulation-only and do not estimate real-world performance.

The supplied synthetic scenarios include `normal`, `sudden_change`,
`unstable_behavior`, `gradual_deviation`, `heavy_sensor_noise`,
`slow_gradual_drift`, and `stealthy_in_range`. P3 training contains only normal
P1 `ProcessUnit` runs; no attack scenario labels are used to train the model.
The two named held-out types are tested in full. `test_scenarios.csv` uses an
independent simulator seed for its one-hour normal run, and the stealthy
channels remain within observed normal ranges. Evaluation labels are used only
after inference and never become model features.

```bash
python3 scripts/evaluate_model.py
python3 -m chem_shield_p3.scripts.evaluate_heldout
python3 scripts/visualize_results.py
```

`evaluate_model.py` computes from actual predictions, with safe zero-division behavior:

- `results/evaluation_results.csv`: accuracy, precision, recall, F1-score, false-positive rate, TP, TN, FP, and FN.
- `results/confusion_matrix.csv`: actual normal/anomaly by predicted normal/anomaly.
- `results/scenario_evaluation.csv`: accuracy, precision, recall, F1, false-positive rate, confusion counts, and detection rate per scenario.
- `results/detection_latency.csv`: first post-onset detection and detection delay in samples for each abnormal scenario. It is not a millisecond measurement.
- `results/detection_latency_summary.csv`: detected/missed scenario totals and mean, median, and maximum detection delay in samples.
- `results/heldout_scenario_evaluation.csv`: detection rate, detection latency in samples/seconds, normal duration, and false alarms per hour for the complete held-out scenarios and normal baseline.
- `results/heldout_evaluation_summary.json`: held-out protocol, training/evaluation counts, and summary metrics.
- `results/ml_errors.csv`: false-positive and false-negative observations with process values and anomaly outputs.
- `graphs/`: motor behavior, anomaly-score, scenario-detection, confusion-matrix, and calculated-metrics plots.

All metrics and figures are generated from the experiment artifacts; no performance numbers are embedded in the scripts or documentation.

## Limitations

This is a one-model, synthetic, controlled academic proof of concept. The baseline is not calibrated or validated for a real operational environment, does not establish cause, and does not identify an attack. It only produces physical-process anomaly evidence for a separate system component to interpret.
