# CHEM-SHIELD OT physical-process monitor

This package adds read-only monitoring for physical telemetry while preserving
the existing Part 1 simulator, HMI, SQLite schema, and Part 4 correlation
contract. It does not issue PLC commands, change setpoints, or substitute for
validated safety interlocks.

## Existing pipeline and field mapping

The Part 1 process simulator is `chem_shield/process/machine.py`; it generates
synthetic state. `chem_shield/process/main.py` stores these values through
`chem_shield/data/store.py`. Existing database fields map to OT fields as:

| OT field | Existing telemetry field | Unit in the Part 1 simulator |
| --- | --- | --- |
| `temperature` | `temperature` | degrees Celsius |
| `pressure` | `pressure` | bar |
| `speed` | `rpm` | revolutions per minute |
| `operating_state` | `motor_status` | `RUNNING` / `STOPPED` |
| `asset_id` | `machine_id` | e.g. `M-01` |

These values are generated by the fictional simulator. No connection to real
equipment is included.

The existing SQLite tables are not modified. The optional storage adapter
reads the current `telemetry` columns in read-only mode and stores output through
the existing `TelemetryStore.add_event()` contract. That table cannot preserve
all rich JSON fields, so persisted event rows map to the existing timestamp,
source, machine_id, event_type, parameter, old_value, new_value, severity
columns. The command-line JSON output retains the richer schema.

Part 4 correlation accepts a smaller object:

```json
{"timestamp":"...Z","asset_id":"M-01","event_type":"physical","anomaly_score":0.7}
```

Use `to_part4_correlation_event()` to adapt a normalized OT alert plus an
anomaly score. Rule alerts remain separate from model scores; a statistical
model result never suppresses a rule violation.

## Setup

Install the main project requirements from the repository root:

```bash
python3 -m pip install -r chem_shield/requirements.txt
```

The physical model uses scikit-learn's `IsolationForest`, NumPy, and joblib;
these are installed as scikit-learn dependencies. The Python environment must
also support the existing CHEM-SHIELD dependencies.

## Configure sensor names, units, limits, and state expectations

Start from `config.example.json`. Sensor aliases and units can be changed under
`sensor_names` and `units`. CSV and database input records must provide numeric
values for all three sensors; missing, non-finite, nonnumeric, stale, duplicate,
or configured-implausible data is reported instead of imputed.

All engineering limits, rate-of-change limits, fluctuation windows,
state-specific ranges, and thresholds are unset (`null`) in the example config.
They must be configured from approved equipment specifications and validated
operating procedures. The checked-in example does not assert safety limits.
`plausibility_ranges` are input-quality bounds and are distinct from engineering
operating limits.

Severity values are explicitly set for each rule configuration or use the
generic default stated in that rule. Validate severity policy with the process
owner before operational use.

## Offline monitoring

Run on the synthetic CSV sample:

```bash
python3 -m chem_shield.ot_monitor.ot_monitor \
  --csv chem_shield/ot_monitor/samples/abnormal_telemetry.csv \
  --config chem_shield/ot_monitor/config.example.json \
  --output /tmp/ot-events.json
```

Run against the existing Part 1 database without writing:

```bash
python3 -m chem_shield.ot_monitor.ot_monitor \
  --database chem_shield/data/telemetry.db \
  --config chem_shield/ot_monitor/config.example.json
```

Persist alert summaries using the existing events table (explicit opt-in):

```bash
python3 -m chem_shield.ot_monitor.ot_monitor \
  --database chem_shield/data/telemetry.db \
  --config path/to/site-config.json \
  --persist
```

No PLC interface is opened by these commands. Database telemetry is selected
using SQLite read-only mode. `--persist` writes only alert summaries to the
existing events table.

## Rules and multivariable anomalies

Deterministic rule checks support configured upper/lower engineering limits,
rate-of-change limits, fluctuation ranges, state-specific sensor ranges, and
speed expectations while running/stopped. These are engineering-limit or
operating-state violations—not statistical anomaly scores.

The optional physical Isolation Forest supports the joint temperature,
pressure, speed, per-minute deltas, and one-hot operating state. The learned
normal baseline captures state-associated multivariable patterns without
hardcoding a supposed physical relationship between sensors. The first
measurement for an asset has zero derivative because no previous observation
is available; sensor values themselves are never imputed.

An anomaly score is a bounded transform of scikit-learn's decision function;
it is a relative anomaly signal, not a calibrated probability or a safety
decision. The default contamination is `0.1`; this configures the statistical
cutoff against baseline data, not an engineering or safety limit.

## Train, evaluate, and persist the physical model

`samples/normal_telemetry.csv` is a synthetic normal baseline. Do not include
abnormal examples in this file. The separate
`samples/abnormal_telemetry.csv` includes labeled held-out normal controls and
controlled abnormal synthetic scenarios.

```bash
python3 -m chem_shield.ot_monitor.train_model \
  --baseline chem_shield/ot_monitor/samples/normal_telemetry.csv \
  --evaluation chem_shield/ot_monitor/samples/abnormal_telemetry.csv \
  --output /tmp/chem-shield-physical-iforest.joblib
```

The report includes precision, recall, F1, false-positive rate, and a confusion
matrix computed on the held-out file. These synthetic example metrics are only
for reproducibility and are not evidence of real-world accuracy. Training
refuses rows explicitly labeled abnormal. `--contamination` may be adjusted
only to follow a documented statistical baseline policy; it must not be used
as an engineering alarm limit. Load the artifact into monitoring:

```bash
python3 -m chem_shield.ot_monitor.ot_monitor \
  --csv chem_shield/ot_monitor/samples/abnormal_telemetry.csv \
  --model /tmp/chem-shield-physical-iforest.joblib
```

Joblib model artifacts should only be loaded from trusted sources.

## Limitations and remaining integration

- Only CSV and the current Part 1 SQLite telemetry schema are implemented as
  input sources. Live PLC/SCADA connectors are not implemented.
- Part 4 correlation is supported through the four-field event converter; this
  package does not start or own the Part 4 engine.
- Persisted alerts are summaries in the legacy `events` table. It has no event
  ID, evidence JSON, measurements, model metadata, or source-origin columns;
  rich output remains available through the JSON stream/output file.
- Synthetic telemetry and synthetic controlled anomalies are for software
  testing only. Obtain actual ranges, units, alarm priorities, state profiles,
  and acceptance criteria from process/equipment specifications before using
  this monitor beyond a lab.
- No automatic actuation, remediation, alarm suppression, or control writes.
